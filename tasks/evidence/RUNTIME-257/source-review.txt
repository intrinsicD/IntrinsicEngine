Two independent reasons, both structural rather than empirical:

1. `Models.cpp` is an **implementation unit** (`module Extrinsic.Runtime.EditorWorkspaceSnapshots;`, no `export`). Its imports never propagate to consumers of the module, so no import edit here can alter the module's exported interface. Public-contract loss is not reachable from this diff.
2. `Runtime.EditorMutation.Internal.hpp` is header-only with **internal linkage throughout**: `InitialMutationState` sits in an unnamed namespace and `ExecuteUndoableEntityMutation` is a `static` template. Each including TU gets its own copy, and the header's own comment anticipates multiple implementation units of one module including it. Dropping the include from one TU is therefore strictly TU-local — no ODR, linkage, or ABI effect on the sibling units that still include it. Given zero token uses of both identifiers, removal is safe.

Dependency direction is monotonically narrower: a re-export facade is replaced by two leaf owners, so any layering rule the file satisfied before it still satisfies. No performance inference drawn from the count change.
